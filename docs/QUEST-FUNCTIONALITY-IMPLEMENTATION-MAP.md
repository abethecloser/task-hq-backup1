# Quest Task HQ — Functionality & Implementation Map

**Scan date:** 2026-10-20  
**Scope:** read-only review of the repository, existing verification records, and the production site's unauthenticated shell. No application behavior, production data, auth policy, database schema, or deployment was changed.

## Executive summary

Task-HQ has a substantial task/workspace foundation: a shared task engine, role checks, an authenticated Supabase dispatch path, revision-aware persistence, workspace activity, and deterministic operational signals. The highest operational risks are not missing screens; they are unproven live multi-user guarantees and mismatches between live mode and features that are explicitly demo-only, preview-only, or unsupported by the deployed dispatch version.

The main product surfaces are implemented, but this scan does **not** certify the current production build end-to-end. `https://task.questroofing.com/` returned HTTP 200 through the authenticated Vercel CLI, which verifies delivery of the app shell only. No approved test-account session was available for an authenticated production walkthrough. A historical owner task create → refresh → reopen test passed on 2026-10-17; current production Realtime, two-user behavior, and negative cross-tenant access checks remain unverified. The current offline Node test run passed **236/236** tests; these tests do not establish deployed Supabase, RLS, or provider behavior.

### Status meanings

- **WORKING** — the stated flow has direct end-to-end evidence.
- **PARTIAL** — some behavior works, but an important persistence, integration, delivery, or live-verification link is absent.
- **UI ONLY** — the visible interaction is local/simulated or does not persist to the shared workspace.
- **BROKEN** — evidence shows an implementation fails.
- **NOT VERIFIED** — evidence is insufficient to claim either success or failure.
- **MISSING** — no implementation or route was found for the stated capability.

## Pass 2 — data flow, provenance and verification

### Verified source-level paths

- **Task change:** signed-in UI action → `quest.dispatch` → authenticated Supabase Edge Function `dispatch` → shared engine/permissions → revision-checked workspace persistence → response/toast and `workspace_state` Realtime. See [`src/adapter/live.ts`](../src/adapter/live.ts#L20), [`supabase/functions/dispatch/handler.ts`](../supabase/functions/dispatch/handler.ts#L41) and [`supabase/functions/dispatch/persistence.ts`](../supabase/functions/dispatch/persistence.ts). Current production parity is not implied by source-level wiring.
- **Membership/access:** People UI → organization RPC → database authorization; platform-admin organization actions use separate `platform_*` RPCs. Invitation creation is not email delivery. See [`src/app/People.tsx`](../src/app/People.tsx#L241) and [`src/live/PlatformConsole.tsx`](../src/live/PlatformConsole.tsx#L44).
- **Task notifications:** current task state + actor + deterministic rules → in-app notification projection. This is not evidence of a durable external notification, recipient delivery receipt or background schedule.
- **Demo channels/tools:** UI → local demo store → browser storage. These do not synchronize across authenticated accounts.
- **New intake candidate:** validated source envelope → approved organization/source/owner → SQL receipt + lead + follow-up + audit. The candidate path is not deployed/verified and Construction remains disabled; it must not be described as a live integration.

### Provenance assessment

Task history and workspace audit foundations can preserve actor, time and action for dispatched work. Reference drafts can travel with workspace actions. Provenance is incomplete at system boundaries: demo messages are local; invitation creation has no delivery receipt; external calendar/email/call sources are not connected; and the candidate intake's source evidence is not a production guarantee. The next release gate should verify actor, target, action, timestamp, result/reason and revision in the deployed audit trail, including denied and failed writes.

## Observed gaps vs. product enhancements

### Observed gaps (supported by current source or existing evidence)

1. Live mode has no shared channel-message store and no shared estimates/proposals store; both stores are explicitly omitted in live mode.
2. Workbook edits are intentionally memory-only and are lost on reload.
3. Calendar appointments, email, phone and external messaging are not connected; normalization contracts do not constitute integrations.
4. The live client advertises task taxonomy as unsupported while source and UI contain taxonomy/task-type features.
5. Invitations are recorded but not sent; a human must complete delivery.
6. Deterministic attention/automation logic exists, but no verified scheduler/background notification delivery was found.
7. The new intake and staged-contact database work is documented as candidate/unverified; no production enablement is authorized.
8. Full authenticated production behavior, real two-user Realtime, live negative tenant-isolation tests, and real-device mobile acceptance were not verified in this pass.

### Product enhancements (not defects unless separately accepted)

- Complete next-step handoff by creating a follow-up task only when an explicit next action, responsible person and authorization are present. Existing dependency unlocks and task handoffs are not the same as creating a new task. This aligns with the dated owner feedback in [`docs/abraham-feedback-2026-10-19.md`](./abraham-feedback-2026-10-19.md#L5).
- Provide shared in-app channels and durable recipient notification receipts.
- Add authorized read-only calendar references; do not infer availability or book appointments.
- Make the workbook operational only after agreeing on ownership, row permissions, history, import/export and mobile editing.
- Add dedicated goals/reminders or general document storage only if a concrete workflow requires them.

## Automation roadmap

All automations below are proposals, not claims of current scheduled delivery. Begin with deterministic rules and in-app outcomes. External communication or consequential business actions require explicit authorization.

| Value / automation | Trigger and condition | Action / recipient | Evidence retained | Failure behavior | Human authority |
|---|---|---|---|---|---|
| High — assignment receipt | A committed task assignment or reassignment to an active member. | Create one in-app notification for the new assignee; optionally inform watchers if that policy is approved. | Actor, task, old/new assignee, time, revision and delivery/read state. | Idempotent retry; show pending/error state if delivery is unavailable; never claim delivery from a local toast. | Existing task permission authorizes assignment; do not send email/text without separate approval. |

## Reusable foundations

- **Shared deterministic task engine and permissions:** `src/core/engine.ts`, `src/core/permissions.ts`, `src/core/rules.ts`, and parity tests. Reuse the same decision logic in UI and server; do not duplicate business rules.
- **Backend boundary:** `QuestBackend` plus live/demo implementations provide a clean persistence seam. Extend the live contract deliberately and keep demo adapters clearly separated.
- **Revision and audit model:** `workspace_state`, optimistic revision checks, workspace events and `audit_log` provide a foundation for durable outcomes; verify deployed behavior before relying on it.
- **Integration contracts:** intake envelope validation, idempotency, scoped calendar normalization and operations client are reusable boundaries, but are not provider connections or authorization by themselves.
- **UI/accessibility patterns:** `TaskControls`, `TaskPage`, `Select`, reference-aware inputs, focus handling and the mobile standard are reusable for operational surfaces.
- **Deterministic signals and metrics:** `src/core/executive.ts` and `src/core/metrics.ts` derive recommendations and measures from existing events; preserve source, sample size and time window.
- **Keep out of production assumptions:** `demoMessaging`, `demoTools`, `OperationsWorkbook` preview, simulated agent workspace and browser-local display preferences are not shared business-data foundations.

## Release decision

No deployment, migration, production data write or behavior change is recommended from this scan alone. First close **T1** and **T2** in an approved staging environment. Keep intake, messaging, calendar, workbook persistence, and automated external notifications behind their specific owner/data-source/permission approvals.
